# Дизайн: игра «Выборы» для детского лагеря

Дата: 2026-08-08
Статус: черновик, на ревью

## 1. Цель

Превратить работающий протокол тайного цифрового голосования
([he-su-pavlov.py](../../he-su-pavlov.py), [lib_blind.py](../../lib_blind.py)) в живую игру для
детского лагеря на телефонах Android c Termux.

Сюжет игры: дети голосуют и играют роли. Один телефон - «агентство» (регистратор + публичное
хранилище), его экран транслируется на стену через проектор. Участники подходят с телефонами,
регистрируются у регистратора (живое взаимодействие + QR), голосуют, а в финале сдают ключи
расшифровки - и голоса «расшифровываются» на глазах у всех. Любой может сам пересчитать
результаты из публичных файлов, не доверяя никому.

Криптографическая математика **не меняется**: слепая RSA-подпись 2048 бит + AES-CTR для
бюллетеней. Изменяется только транспорт (обмен через FTP вместо памяти) и появляется игровая
оболочка (QR, экран статуса, стена).

## 2. Архитектура

- **Обмен - через FTP-сервер** в лагере (организует ведущий). Все телефоны ходят в общие папки;
  документы только **добавляются** (append-only): файлы уникальны по имени, удаление/перезапись
  запрещены настройкой сервера и не используются скриптами.
- **Один набор скриптов**, роль выбирается при запуске:
  - `elector.py` - участник;
  - `agency.py` - агентство/регистратор (приём регистрации, обработка документов, стена, смена фаз);
  - `verify.py` - независимая проверка голосов из публичных файлов.
- **QR-коды** используются только для живого рукопожатия при регистрации (участник показывает
  метку регистратору). Вся остальная коммуникация - файлами через FTP.
- **Публикация одобрений пучками** и анонимные метки - чтобы тайминг не раскрывал участников.
- Показ на стене - статичная HTML-страница `meta/index.html` на FTP (режим `agency.py --wall`),
  сама перезагружается JS-таймером каждые 20 секунд; открывается по FTP-адресу с любого устройства.

## 3. Структура папки `game/`

```
game/

  protocol.py         # папки FTP, форматы документов (JSON), сериализация, проверки
  sync.py             # обёртка над ftplib: листинг/скачивание/загрузка, append-only имена
  agency.py           # консоль агентства/регистратора + режим --wall
  elector.py          # мастер участника
  verify.py           # независимый подсчёт из публичных файлов

  tests/

    test_protocol.py

    termux_smoke.md
  README.md           # инструкция на русском (установка, роли, сценарий игры)
```

## 4. Папки на FTP

Каждый документ - маленький JSON-файл с уникальным именем `<ключ>-<ВВВВММДДЧЧММСС>-<случайное>.json`
(append-only естественным образом). `meta/` - одиночные служебные файлы.

| Папка | Содержимое |
|---|---|
| `meta/pubkey.txt` | публичный ключ регистратора (PEM, один файл) |
| `meta/candidates.json` | название выборов + список кандидатов |
| `meta/phase.txt` | текущая фаза: `REGISTRATION` / `VOTING` / `KEYS` / `RESULT` |
| `marks/` | одобренные регистратором метки (только номера, без ников) |
| `sign-requests/` | слепые запросы участников (mark + blinded) |
| `sign-results/` | слепые подписи регистратора |
| `authorized-keys/` | авторизованные публичные ключи избирателей |
| `ballots/` | все присланные шифрованные бюллетени (учтённые и нет) |
| `secret-keys/` | ключи расшифровки (только для учтённых бюллетеней) |

## 5. Форматы документов

Все JSON - отформатированные (`indent=2`, `ensure_ascii=False`, кириллица как есть).

`meta/pubkey.txt`:
```
-----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA...
-----END PUBLIC KEY-----
```

`meta/candidates.json`:
```json
{
  "election": "Выборы Кота-президента",
  "candidates": [
    { "id": 1, "name": "Кандидат №1" },
    { "id": 2, "name": "Кандидат №2" },
    { "id": 3, "name": "Против всех" }
  ]
}
```

`meta/phase.txt` - просто текст фазы: `REGISTRATION`.

`marks/<mark>-<ts>.json`:
```json
{
  "mark": 17,
  "approved_at": "2026-08-08T12:34:56"
}
```

`sign-requests/<mark>-<ts>.json`:
```json
{
  "mark": 17,
  "blinded": 11837491827364918374619837
}
```

`sign-results/<mark>-<ts>.json` (поле `blinded` повторено для сопоставления):
```json
{
  "mark": 17,
  "blinded": 11837491827364918374619837,
  "sign": 828171837464837463
}
```

`authorized-keys/<mark>-<ts>.json`:
```json
{
  "mark": 17,
  "public_key_pem": "-----BEGIN PUBLIC KEY-----\nMIIBIjANBgkqhkiG9w0B...\n-----END PUBLIC KEY-----",
  "key_sign": 91827364518
}
```

`ballots/<mark_2>-<ts>.json`:
```json
{
  "mark_2": 987654321,
  "public_key_pem": "-----BEGIN PUBLIC KEY-----\nMIIBIjANBgkqhkiG9w0B...\n-----END PUBLIC KEY-----",
  "ballot_enc_b64": "Mg==",
  "ballot_sign": 8473648374
}
```

`secret-keys/<mark_2>-<ts>.json`:
```json
{
  "mark_2": 987654321,
  "public_key_pem": "-----BEGIN PUBLIC KEY-----\nMIIBIjANBgkqhkiG9w0B...\n-----END PUBLIC KEY-----",
  "secret_key_b64": "4a8f2c1b0d9e7f6a0b2c4d6e",
  "key_sign": 7364738264
}
```

## 6. Протокол и фазы

Фаза хранится в `meta/phase.txt`, переключает агентство. Участник ориентируется по фазе.

**Фаза 0 · СТАРТ.** Агентство генерирует ключи, публикует `meta/pubkey.txt`,
`meta/candidates.json`, пишет `REGISTRATION`.

**Фаза 1 · РЕГИСТРАЦИЯ.**
1. Участник запускает `elector.py`: генерирует пару RSA-ключей, случайную метку-номер
   (плюс ник - только на его экране), заливает слепой запрос в `sign-requests/`, показывает
   QR-метку.
2. Участник подходит к регистратору. Регистратор лично видит человека, сканирует QR (или вводит
   номер вручную), подтверждает «принять». Одобрения копятся и выгружаются **пучками** в `marks/`.
3. Фоновый цикл агентства подписывает слепые запросы тех меток, что уже в `marks/`, пучками же
   выкладывает подписи в `sign-results/`.
4. Участник забирает свою подпись, расслепляет её, заливает запрос авторизации ключа
   (`public_key_pem` + `key_sign`) в `authorized-keys/`.
5. Агентство проверяет подпись регистратора на ключе → публикует ключ в списке авторизованных.

`elector.py` на экране участника показывает живой статус:
```
МЕТКА #17 (Кот)
────────────────
Регистрация: … ожидание          →  ✅ ВЫ ДОПУЩЕНЫ
Подпись ключа: … ожидание        →  ✅ получена
Авторизация ключа: …             →  ✅ ваш ключ в списке
```

**Фаза 2 · ГОЛОСОВАНИЕ.** Участник выбирает кандидата, шифрует номер кандидата AES-CTR
своим случайным ключом, подписывает шифротекст, заливает в `ballots/`. Агентство принимает
**все** бюллетени в публичный рекорд. Ключи расшифровки на этой фазе не принимаются.

**Фаза 3 · ВЫДАЧА КЛЮЧЕЙ.** Регистратор закрывает голосование (кнопка). Участники заливают
свои ключи расшифровки в `secret-keys/` - принимаются только для уже опубликованных и учтённых
бюллетеней. Это драматичный момент «ключи начинают появляться».

**Фаза 4 · ИТОГ.** На стене - расшифрованные голоса и итоговая таблица.

**Учтён/не учтён** не хранится в файле, а **выводится при чтении** (единая функция в
`protocol.py`, её используют и агентство, и `verify.py`):
- публичный ключ бюллетеня не в `authorized-keys/` → ❌ НЕ УЧТЁН (избиратель не зарегистрирован);
- подпись бюллетеня неверна → ❌ НЕ УЧТЁН (подпись неверна);
- иначе → ✅ УЧТЁН.
В подсчёт идут только учтённые. Бюллетени вне списка видны на стене - это и есть демонстрация
защиты от вбросов: попытка видна, голос не засчитан.

**Что, если проголосовать без регистрации?** - Бюллетень появится в `ballots/`, но будет
«НЕ УЧТЁН (избиратель не зарегистрирован)».

**Почему это понятно?** Потому что проверку делает любой сам, никому не веря на слово: в
бюллетене есть публичный ключ участника, а в списке `authorized-keys/` этого ключа нет -
регистратор его никогда не авторизовал. Ключ либо есть в списке допущенных, либо его там нет;
это видно каждому прямо в публичных файлах. Считать такой бюллетень нельзя, и любой наблюдатель
убеждается в этом сам, заглянув в `authorized-keys/`.

**Непрерывный подсчёт.** После каждого нового публичного документа агентство (и `verify.py`)
пытается расшифровать каждый учтённый бюллетень каждым опубликованным ключом: пока ключа нет -
«пока не расшифровывается…», как только появился - «расшифрован: Кандидат №N».

## 7. Приватность регистрации

1. **Анонимные метки.** В публичном рекорде (`marks/`, `sign-requests/`, `authorized-keys/`)
   только случайные номера. Ник живёт на экране участника и у регистратора. Стена показывает
   «Метка #17 - допущен», не имя.
2. **Выгрузка пучками.** Агентство копит одобрения и публикует пачкой (раз в ~25 сек или по
   3–5 штук, в случайном порядке). Подписи обрабатываются пучками аналогично. Связь
   «только что вышел от регистратора → его файл появился» рвётся.
3. Голос анонимен по построению: бюллетени и ключи связаны с `mark_2` и публичным ключом,
   связь `mark_1` ↔ `mark_2` известна только участнику; слепая подпись скрывает ключ от
   регистратора.
4. **Зачем метка, если её можно украсть?** Метка - просто «кто ты». Сама по себе она ничего
   не даёт: без ключа и подписи голос не учтут, даже если метку украсть. Можно и вовсе без
   метки - просто тогда всем, чтобы себя найти в списках, придётся «читать» все документы и
   искать там «свой запрос» по данным. Метка - это ярлык, по которому каждый мгновенно
   находит свои файлы среди чужих, не раскрывая при этом, кто он.

## 8. QR-механика регистрации

- QR рисуется `segno` прямо в терминале (Unicode-полублоки), картинки не нужны.
- Кириллица в QR - через UTF-8.
- Регистратор сканирует: `termux-camera-photo` (снимок) + `pyzbar` (ctypes) с системной `zbar`.
- Fallback: ручной ввод номера метки (камера/декодер могут сбоить на конкретном телефоне).

## 9. Стена на FTP (`meta/index.html`, режим `agency.py --wall`)

Агентство **не держит собственный HTTP-сервер**: оно вычисляет HTML-страницу стены и
**публикует её на FTP** как `meta/index.html` (статичный файл, без внешних ресурсов -
работает и по `ftp://`, и из скачанного файла). Любой может открыть её в браузере по адресу
`ftp://<сервер>/<база>/meta/index.html` с любого устройства в сети и смотреть с автообновлением.

- В страницу встроен JS-таймер: `setTimeout(location.reload, 20000)` - страница сама
  перезагружается **каждые 20 секунд**.
- Агентство пересчитывает и перезаливает страницу каждые ~15 секунд (фоновый цикл в
  `--wall`-режиме). Страница показывает «обновлено в <время>».
- Содержимое: фаза, допущенные метки, авторизованные ключи, бюллетени (✅/❌), ключи
  расшифровки, живой подсчёт и вопросы-ответы «почему так устроено» для текущей фазы.
- **`meta/index.html` - единственный файл, который перезаписывается** (это «живой экран»,
  производный от append-only документов). Все документы рекорда остаются append-only.
- Терминальный режим `agency.py` - для управления, сканирования и смены фаз.

## 10. `install.sh` (Termux, `curl URL | sh`)

Пользователь выполняет:
```
curl https://ЛАГЕРЬ/vote-game/install.sh | sh
```

Скрипт: `pkg update`, установка `python termux-api clang zbar`, pip-зависимости
(`pyaes segno pyzbar`), PyCryptodome через `pkg install python-pycryptodome || pip install
pycryptodome` (сборка требует `clang`); создание `$HOME/vote-game`; скачивание и распаковка
`vote-game.tar.gz` с базового URL; вывод подсказки по запуску ролей. Базовая URL - константа
в начале `install.sh`, настраивается перед публикацией.

Терминальные библиотеки на Termux (bionic, не glibc): pyaes/segno/pyzbar - чистый Python,
ставятся без проблем; PyCryptodome - из репозитория Termux или сборка из исходников.

## 11. Тесты

`game/tests/` на обычном Linux (pip, без Termux), отдельно ручной смок-тест на телефоне:
- `test_crypto.py` - слепая подпись туда-обратно, верификация, границы 2048.
- `test_protocol.py` - проверки агентства: ключ без подписи регистратора отклонён; бюллетень от
  незарегистрированного - НЕ УЧТЁН; плохая подпись - НЕ УЧТЁН; ключ расшифровки без
  опубликованного учтённого бюллетеня - отклонён; фаза `KEYS` не принимает бюллетени.
- `test_game_e2e.py` - полный прогон игры: локальный FTP-сервер (pyftpdlib, dev-зависимость),
  агентство + участники (зарегистрированные, один незарегистрированный, один с испорченной
  подписью) → публичный рекорд, статусы, сходимость итога, вброс не учтён, `verify.py` даёт
  тот же результат.
- `termux_smoke.md` - чек-лист ручного прогона: агентство на проекторе + 2 участника.

## 12. Устойчивость

- Повторные попытки и понятные русские сообщения при недоступности FTP.
- Уникальные имена файлов исключают перезапись; дубли-документы отбрасываются по ключу
  (mark / mark_2 / содержимое).
- Ручной ввод метки как fallback сканирования.
- Сервер FTP настраивает ведущий: разрешить загрузку, запретить удаление/перезапись
  (append-only). Скрипты этому не препятствуют.

## 13. Вне рамок (на потом)

- Пароли/сроки действия меток, защита от replay.
- Поддержка нескольких раундов голосования без переустановки.
- Красивая графика на стене (сейчас - простая HTML-страница).
