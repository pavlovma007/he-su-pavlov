# Тайные выборы на эллиптических кривых

### Логика голосования, передаваемые данные и сложность раскрытия

Этот документ описывает тот же протокол тайного голосования, что и текущая
RSA-версия (`lib_blind.py`), но с криптографией на **эллиптических кривых**.
Отдельно разбирается, какие структуры данных и куда передаются, и почему
**расшифровка** и **деанонимизация** - это либо вычислительно нереальная задача,
либо (для регистратора) задача, которая **математически невозможна**.

---

## 1. Зачем эллиптические кривые

В RSA-версии все подписи - это возведение числа в степень по модулю `n`
(числа по 2048 бит). На эллиптических кривых «умножение» происходит в группе
точек кривой, и для равной стойкости нужны ключи **в разы короче**:

| Схема | Размер ключа | Сложность взлома |
|---|---|---|
| RSA-2048 | 2048 бит | ~2¹¹² операций |
| **EC P-256** (secp256r1) | 256 бит | **~2¹²⁸ операций** |

То есть EC-вариант не только короче, но и **стойче** за тот же объём данных.

Главное, что это даёт протоколу: на кривых существует стандартная **слепая
подпись Blind Schnorr** - прямой аналог слепой подписи Чаума из RSA-версии,
с тем же главным свойством: **подписывающий не знает, что именно он подписывает,
и не может впоследствии связать подпись с транзакцией.**

---

## 2. Математическая база (немного математики)

Эллиптическая кривая - это множество точек, на котором задано «сложение»
(геометрическое правило: прямая через две точки даёт третью). Ключевые объекты:

- **`G`** - фиксированная точка-генератор кривой.
- **`q`** - простое число - порядок точки `G` (для P-256 это 256-битное простое).
- **Скалярное умножение:** `P = x·G` - это сложить точку `G` саму с собой `x` раз.
- **Задача дискретного логарифма (ECDLP):** зная `G` и `P`, найти `x` такой,
  что `P = x·G`.

Прямое действие (умножить) - быстрое. Обратное (по `P` найти `x`) - для
правильно выбранной кривой **вычислительно неразрешимо**: лучший известный
алгоритм (метод Полларда «ро») требует порядка **2¹²⁸** групповых операций.
Это больше, чем может сделать вся вычислительная мощность планеты за разумное
время.

- **`H(...)`** - криптографический хэш SHA-256.
- **`||`** - конкатенация байтов.

Обозначения действующих лиц:

| Символ | Кто | Что это |
|---|---|---|
| `y`, `Q = y·G` | **Регистратор** | приватный скаляр и публичная точка |
| `x`, `P = x·G` | **Избиратель** | приватный скаляр и публичная точка |
| `m` | - | подписываемое сообщение = хэш публичного ключа избирателя |
| `α, β, k` | - | одноразовые случайные числа (маски) |

Все операции со скалярами (`+`, `·`) выполняются **по модулю `q`**.

## 3. Слепая подпись Blind Schnorr

Слепая подпись нужна для одного шага регистрации: **регистратор должен подписать
публичный ключ избирателя, не видя его** - чтобы потом не мог связать «кто
зарегистрировался» с «каким ключом голосует».

В RSA это были 2 раунда (избиратель слепил, регистратор подписал). Blind Schnorr
требует **3 раунда**: сначала регистратор присылает «коммит» (обязательство),
потом избиратель присылает ослеплённый вызов, потом регистратор присылает ответ.

### Шаг 0. Регистратор: коммит (обязательство)

```
Регистратор выбирает случайный k, вычисляет R = k·G
и отправляет избирателю точку R.
```

Здесь `k` - одноразовый секрет. **Одна подпись - один свежий `k`.**

### Шаг 1. Избиратель: слепит и отправляет вызов

```
Избиратель выбирает случайные маски α, β.
Вычисляет:
    R' = R + α·G + β·Q      (ослеплённый коммит - скрывает R)
    c' = H(R' || m)         (настоящий вызов на сообщении m)
    c  = (c' + β) mod q     (ослеплённый вызов)
и отправляет регистратору число c. Маски α, β и точку R' держит при себе.
```

### Шаг 2. Регистратор: отвечает

```
Регистратор вычисляет s = (k + c·y) mod q
и отправляет избирателю число s.
```

### Шаг 3. Избиратель: расслепляет

```
Избиратель вычисляет s' = (s + α) mod q.
Готовая подпись регистратора на ключе избирателя: σ = (R', s').
```

### Проверка (любой желающий)

Любой, у кого есть `m`, подпись `(R', s')` и публичный ключ регистратора `Q`,
проверяет одно равенство:

```
s'·G  =  R' + H(R' || m)·Q
```

**Почему это работает** (короткое алгебраическое доказательство):

```
s'·G = (k + c·y + α)·G = k·G + c·y·G + α·G = R + c·Q + α·G

R' + c'·Q = (R + α·G + β·Q) + c'·Q = R + α·G + (β + c')·Q = R + α·G + c·Q
```

Обе стороны равны, т.к. `c = c' + β`. Значит подпись `(R', s')` - это
**обычная подпись Шнорра** на сообщении `m`, и она честно проверяется любым.

### Почему это «слепая» подпись

Регистратор видит только свой коммит `R`, ослеплённый вызов `c` и отвечает `s`.
Он **не видит** ни `m`, ни `R'`, ни масок. Случайные `α, β` полностью скрывают
связь между тем, что регистратор подписал, и тем, что избиратель получил.
Подробный анализ слепоты - в разделе 7.

## 4. Протокол голосования на EC

Весь протокол - те же 4 фазы, что в RSA-версии: **REGISTRATION → VOTING →
KEYS → RESULT**. Обмен идёт через общий FTP-каталог: каждый участник кладёт
JSON-файлы в общие папки. EC-вариант отличается **только** фазой регистрации
(добавляется раунд коммита) и форматом подписей (пара точек/чисел вместо одного
числа).

### Фаза REGISTRATION (EC)

```
Избиратель                    Регистратор (агентство)
    |                                |
    |  (1) sign-requests/M1: step0   |
    |-------------------------------->|
    |        (2) sign-results/M1:    |
    |            commit = R   <------|
    |                                |  генерирует k, R=k·G, k держит в секрете
    |  (3) sign-requests/M1: step1,  |
    |            challenge = c      |
    |-------------------------------->|
    |        (4) sign-results/M1:   |
    |            s            <------|  s = k + c·y
    |  (5) s' = s + α, подпись=(R', s')
    |  публикует в authorized-keys:
    |      {public_key_pem, key_sign={R', s'}}
```

Тонкость: регистратор **обязан помнить** `k` между раундами (2) и (4).
В RSA-версии подпись была «без памяти» (`pow(blinded, d, n)`), а здесь
появляется состояние. При перезапуске агентства незавершённые EC-регистрации
придётся повторить.

### Фаза VOTING (EC)

```
Избиратель:
  1) шифрует свой выбор симметричным шифром AES-CTR ключом secret_key
     (ключ выводится из его приватного скаляра, нигде не публикуется);
  2) подписывает шифротекст ct СВОИМ приватным ключом (обычная подпись Шнорра):
        ballot_sign = SchnorrSign(ct, x);
  3) публикует в ballots/M2:
        {mark_2, public_key_pem, ballot_enc_b64, ballot_sign={R, s}}.
```

### Фаза KEYS (EC)

```
Избиратель публикует в secret-keys/M2 ключ расшифровки:
    {mark_2, public_key_pem, secret_key_b64, key_sign={R, s}}.
```

Ключ публикуется **только после закрытия голосования** - до этого расшифровать
бюллетень невозможно (см. раздел 6).

### Фаза RESULT (EC)

Любой желающий скачивает все публичные файлы и **независимо пересчитывает итог**:

```
для каждого authorized-keys:
    проверить слепую подпись регистратора:  s'·G == R' + H(R'||m)·Q
для каждого ballots:
    проверить подпись избирателя:            s·G == R + H(R||ct)·Q_v
    если верна - расшифровать AES ключом из secret-keys, распознать кандидата
итог = сумма по кандидатам
```

## 5. Структуры данных: что и куда передаётся

| Папка / файл | Кто пишет | Кто читает | Содержимое (EC) | Зачем |
|---|---|---|---|---|
| `meta/pubkey.txt` | регистратор | все | публичный ключ регистратора `Q` (PEM) | проверка подписей регистратора |
| `meta/candidates.json` | регистратор | все | список кандидатов | ввод в фазу VOTING |
| `meta/phase/*.json` | регистратор | все | смена фаз с таймстампом | запрет позднего голосования |
| `marks/M1.json` | регистратор | избиратель | одобренные метки | допуск к подписи |
| `sign-requests/M1.json` | избиратель | регистратор | `step0: {mark, crypto:"ec", step:0}` → `step1: {..., step:1, challenge:c}` | слепая подпись, раунды 1 и 3 |
| `sign-results/M1.json` | регистратор | избиратель | `step0: {..., commit:R}` → `step1: {..., s}` | слепая подпись, раунды 2 и 4 |
| `authorized-keys/M1.json` | избиратель | все | `{public_key_pem, key_sign:{R', s'}}` | доказательство допуска к голосованию |
| `ballots/M2.json` | избиратель | все | `{mark_2, public_key_pem, ballot_enc_b64, ballot_sign:{R, s}}` | зашифрованный голос |
| `secret-keys/M2.json` | избиратель | все | `{mark_2, public_key_pem, secret_key_b64, key_sign:{R, s}}` | ключ расшифровки после голосования |

Формат значений:

- **точка кривой** (`R`, `R'`, `Q`, `P`) - сериализуется как 65 байт
  (несжатая форма: префикс `0x04` + `x` + `y`) и кодируется base64;
- **скаляр** (`s`, `c`, `s'`) - целое число по модулю `q`;
- **подпись** - это **пара** `{R, s}`, а не одно число как в RSA;
- **PEM** - стандартная сериализация ключей EC (открытый/закрытый).

### 5.1. Как участники находят свои документы в общей куче

Общий каталог на FTP - это «общая куча»: все пишут в одни и те же папки, файлы
идут вперемешку в хронологическом порядке. Вопрос «как найти СВОЁ» решается
одним простым механизмом.

**Принцип: у каждого публикуемого документа есть имя файла - случайная метка,
которую знает только его владелец.** По сути это не «метка», а просто имя файла:
случайное число, генерируется владельцем и хранится локально (в state-файле рядом
с ключом, права 600). Владелец находит свой документ **одним запросом** -
«прочитай файл, имя которого начинается с моей метки», - и не скачивает и не
просматривает весь каталог. Чтобы убедиться, что документ его, он проверяет:
имя совпало и внутри содержится та же метка.

Метка НЕ выводится из ключа и НЕ связана с личностью: посторонний не может
вычислить, какие файлы принадлежат конкретному участнику.

```
Участник и его документы:

  метка-1 → sign-requests/{метка-1}-….json   (запрос на подпись)
  метка-1 → sign-results/{метка-1}-….json    (подпись регистратора)
  метка-2 → authorized-keys/{метка-2}-….json (авторизация ключа)
  метка-3 → ballots/{метка-3}-….json         (бюллетень)
  метка-3 → secret-keys/{метка-3}-….json     (ключ расшифровки)
```

У каждого участника свой набор случайных меток; чужие метки ему неизвестны, а
свои он не разглашает.

**Кому метки не нужны.** Тому, кто считает итог или проверяет подписи (аудитор,
стена, независимый пересчёт), читать нужно **всё** - он проходит по каталогу
целиком. Метки для него не механизм «найти своё», а просто часть имён файлов.

**Единственная метка, видимая другим.** Одна метка (регистрационная, `метка-1`)
показывается регистратору вживую через QR - чтобы он знал, какой запрос
подписать. Это тоже случайное число, не связанное ни с ключом, ни с остальными
метками владельца.

**Связь с анонимностью.** Поскольку метки случайны и не выводимы из публичных
данных, даже регистратор, видевший `метка-1` вживую, не может вычислить ни ключ,
ни остальные метки владельца (разбор утечки в текущей реализации - раздел 7.4,
предложение - раздел 8).

Метки - не обязательный элемент: их роль - просто «список адресов своих
документов». Альтернатива - личный индексный файл, но случайные имена проще и
не требуют отдельного механизма.

## 6. Сложность расшифровки

Расшифровать бюллетень - значит узнать голос избирателя **до** публикации ключа
в фазе KEYS. Все пути упираются в вычислительно неразрешимые задачи:

| Способ расшифровать | Сложность | Вердикт |
|---|---|---|
| Перебор AES-ключа (128 бит) | 2¹²⁸ проверок | невозможно на практике |
| Вычислить приватный скаляр `x` из публичной точки `P` | ECDLP на P-256: ~2¹²⁸ операций | невозможно на практике |
| Вычислить приватный скаляр `y` регистратора из `Q` | ECDLP: ~2¹²⁸ операций | невозможно на практике |
| Подобрать маски `α, β` из подписи `(R', s')` | каждая подпись - свежие случайные маски | не даёт ничего |

Ключ расшифровки выводится из **приватного** скаляра избирателя, который никогда
не публикуется. Значит, до фазы KEYS ключ знает только избиратель. Число 2¹²⁸ -
это больше, чем число атомов в известной части Вселенной; даже если объединить
всю вычислительную мощность планеты, перебор невозможен.

**Вывод:** расшифровка чужого голоса в фазе голосования - задача **вычислительно
нереальная** (2¹²⁸). Это сознательное свойство схемы: ключи публикуются только
после закрытия голосования, поэтому ни подкуп, ни принуждение не могут проверить
«как ты проголосовал», пока голосование идёт.

## 7. Деанонимизация: сложность и невозможность

Надо различать два разных вопроса - их часто путают.

### 7.1. Регистратор ↔ подпись (слепота) - математически невозможно

Вопрос: может ли регистратор, подписавший вслепую ключ, впоследствии сказать
«вот эта подпись `(R', s')` - это тот самый ключ, который я подписал в момент T»?

**Ответ: нет, и не «очень трудно», а математически невозможно - даже при
бесконечной вычислительной мощности.**

Аргумент. Регистратор видел в транзакции только `(R, c, s)`. Готовая подпись -
`(R', s', m)`. Связка между ними - это ровно пара масок:

```
α = (s' − s) mod q
β = (c − H(R' || m)) mod q
```

Маски `α, β` - случайные и равномерные, регистратор их не знает. Для **любой**
подписи из опубликованного пула и **любой** транзакции регистратора существует
ровно одна пара `(α, β)`, которая делает их совместимыми. Все пары
«транзакция ↔ подпись» для регистратора **неразличимы**. Значит, информации для
связывания он не получает вообще: слепота Blind Schnorr - **информационно-
теоретическая**, она не зависит от мощности компьютера.

**Оговорка (важная):** свойство работает только при дисциплине nonce.
Регистратор должен на каждую подпись брать **свежий случайный `k`**. Если одно
и то же `k` используется для нескольких сессий, атакующий получает связанные
уравнения и схема разрушается (известная ROS-атака). Также слепота не защищает
от «внешних» корреляций: IP-адреса, тайминги, камеры - если избиратель сам
раскрыл, какой запрос его, связь восстановится.

### 7.2. Тайна голоса в фазе голосования - вычислительно невозможно

Вопрос: может ли посторонний (или подкупщик, или регистратор) узнать, **как
проголосовал** конкретный избиратель, пока голосование идёт?

Ответ: нет - см. раздел 6. Голос зашифрован AES, ключ публикуется только после
закрытия голосования. Дешифровка требует 2¹²⁸ операций. Это и есть защита от
подкупа/принуждения: «продавец голоса» не может предъявить доказательство, что
проголосовал так, как его просили, пока идёт голосование.

### 7.3. Что раскрыто по дизайну (честные пределы)

Схема не обещает полной анонимности личности - и это **осознанное свойство**:

1. **Кто участвовал - видно.** Бюллетень лежит в открытом каталоге под именем
   `mark_2` и содержит открытый ключ избирателя (`public_key_pem`), а обе метки
   `mark_1`/`mark_2` вычисляются из этого же ключа (подробный разбор - 7.4).
   Регистратор, видевший метку `mark_1` вживую (QR на экране телефона), может по
   списку авторизованных ключей найти, какой ключ соответствует этой метке, а по
   ключу - найти бюллетень. Итог: **«кто участвовал» открыт** - это прямо
   требуется в README («можно узнать, кто принимал участие, а кто - нет»).

2. **После фазы KEYS голос можно сопоставить с личностью - но это НЕ требование
   пересчёта, а следствие текущей реализации меток.** Для пересчёта достаточно
   посчитать голоса; сопоставление «кто - что» ему не нужно. Связь возникает
   потому, что метки выведены из открытого ключа (раздел 7.4). В разделе 8
   предложен вариант, где этой связи нет.

3. Значит, слепая подпись защищает не «полную анонимность», а **недоказуемость
   связи регистрации с моментом подписи**: регистратор не может составить
   достоверную базу «какой ключ подписан когда», которую потом можно скрестить с
   видеонаблюдением и таймингами. Именно это и делает подкуп/принуждение
   недоказуемым изнутри.

**Итоговая оценка деанонимизации:**

| Связка | Можно ли раскрыть | Почему |
|---|---|---|
| Транзакция слепой подписи ↔ подпись | **невозможно** (даже при бесконечной мощности) | информационно-теоретическая слепота, раздел 7.1 |
| Голос ↔ избиратель, до фазы KEYS | **вычислительно невозможно** | AES-128 + ECDLP, раздел 6 |
| Кто участвовал ↔ личность | открыто по дизайну | публичный ключ и метки в открытых файлах |
| Голос ↔ избиратель, после фазы KEYS | сейчас открыто, **но это устранимо** | следствие вывода меток из ключа (7.4) → предложение в разделе 8 |

### 7.4. Метки: почему «две метки» сейчас не дают анонимности

Замысел меток был правильный: на разных этапах - разные псевдонимы, чтобы нельзя
было связать регистрацию с голосом. Но в текущей игре обе метки выводятся из
**одного и того же открытого ключа**:

```
mark_1 = SHA256(DER + "mark-1") mod 2^63   - регистрация (QR регистратору)
mark_2 = SHA256(DER + "mark-2") mod 2^63   - имя файла бюллетеня
```

а сам бюллетень содержит открытый ключ избирателя (`public_key_pem`). Отсюда -
железная цепочка:

```
регистратор видит mark_1 вживую (QR на телефоне избирателя)
  → знает алгоритм (он в открытом коде)
  → по списку авторизованных ключей вычисляет mark_1 для каждого
    и находит ключ избирателя
  → открывает ballots/{mark_2}.json (в файле тот же public_key_pem)
  → после фазы KEYS расшифровывает голос.
```

Проверено скриптом по реальному алгоритму (`ElectorEngine._derive_mark` из
`game/elector.py`): ключ находится по физической метке за один проход.

В старой версии `he-su-pavlov.py` метки были **случайными**
(`mark_1 = random.randint(...)`), и такой жёсткой связи не было. Игра заменила
случайные метки на производные от ключа, чтобы после перезапуска телефона метки
(и личность) не терялись. Это и стало источником утечки: метки полезны как
«адрес своего файла», но производность от открытого ключа делает их же
связующим звеном «личность → голос».

**Вывод:** метки выполняют свою роль (избиратель находит свой файл в публичном
хранилище, не читая всё подряд - см. раздел 5.1), но в текущей реализации они же
позволяют регистратору вычислительно восстановить связь «личность → голос».
Предложение по исправлению - раздел 8.

## 8. Предложение: как убрать связь «личность → голос»

Принцип. Привязка, по которой пользователь находит **свой** файл (механизм -
раздел 5.1), должна быть известна только ему: случайная метка-имя, хранящаяся у
него локально и не выводимая из публичных данных. А сами файлы не должны
содержать публичной привязки к открытому ключу владельца.

### Вариант A - лёгкий (случайные метки-имена + файл состояния)

Метка - это просто **случайное имя файла**, которое знает только владелец
(механизм поиска - раздел 5.1). Хранится в state-файле рядом с ключом:

```
mark_1 = случайное число   - регистрация (QR регистратору)
mark_2 = случайное число   - авторизация ключа
mark_3 = случайное число   - бюллетень и ключ расшифровки
```

Ни одна метка не выводится из ключа - посторонний не может вычислить, какие
файлы чьи. `authorized-keys` НЕ именовать по `mark_1`, иначе регистратор прочтёт
в файле открытый ключ.

- Что получаем: алгоритмическая связь «личность → ключ → бюллетень» исчезает.
- Что остаётся: **тайминг-корреляция** - регистратор знает, когда одобрил
  человека, а новые авторизации и бюллетени появляются после этого. При малом
  числе участников (лагерная игра) догадаться всё ещё можно. Простой шаг,
  но не панацея.
- Плата: метки нужно хранить (state-файл); потеря файла = потеря «адресов»
  своих документов (сами документы в каталоге не пропадают).

### Вариант B - рекомендуемый (анонимный токен, без открытого ключа в бюллетене)

**Регистрация.**
Избиратель генерирует случайный токен `t` (например 32 байта) и **слепо
подписывает** `H(t)` у регистратора - те же 3 раунда Blind Schnorr (раздел 3).
Регистратор одобрил `mark_1` один раз → одна слепая подпись → **один токен на
избирателя**. Сам `t` регистратор не видит (слепота).

**Голосование.**
```
бюллетень = { locator, шифр_голоса, t, подпись_регистратора(t) }
locator    = mark_2 = H(priv_der + "mark-2")   - приватный адрес, знает только избиратель
```
Открытого ключа избирателя в бюллетене **нет вообще**.

**Подсчёт** (независимый, для всех): проверить подпись регистратора на `H(t)`
(легитимность), убедиться, что токен `t` ещё не использовался (один голос на
избирателя), расшифровать AES после фазы KEYS, посчитать.

**Анонимность.** Регистратор не знает `t`; нет ни одного файла, связывающего
`mark_1 ↔ t`; приватный `locator` он вычислить не может. Тайминг-корреляция не
работает - в публичном пространстве просто нет сущности, которую можно
сопоставить с конкретным человеком.

**Плата за вариант B** (честно):
- токен - новый секрет: либо хранить в файле ключа, либо выводить
  детерминированно из приватного ключа (переживает перезапуск телефона);
- кража токена = кража голоса (та же модель риска, что кража приватного ключа);
- роль открытого ключа в голосовании исчезает - легитимность даёт токен;
- **«кто проголосовал, а кто нет» становится непубличным**: известно только
  число использованных токенов. Если требование «видно, кто участвовал» из
  README обязательно, это несовместимо с полной анонимностью голоса - нужен
  компромисс.

**Обновлённая оценка деанонимизации (вариант B):**

| Связка | Можно ли раскрыть |
|---|---|
| Транзакция слепой подписи ↔ подпись | невозможно (информационно-теоретически) |
| Голос ↔ избиратель, до фазы KEYS | вычислительно невозможно (2¹²⁸) |
| Регистратор ↔ какой токен/бюллетень | невозможно (не знает `t`, нет связующего файла) |
| Кто допущен к голосованию | открыто (регистратор видит людей при допуске) |
| Голос ↔ личность, после фазы KEYS | из протокола утечки нет; остаётся только внешняя корреляция (камера, тайминги), которой не помогают публичные данные |

## 9. Предостережения реализации (если будем делать код)

1. **Nonce `k` регистратора** - одна подпись, один свежий секретный `k`.
   Повторное использование - фатально (ROS-атака).
2. **Случайные `α, β` избирателя** - честный CSPRNG, не переиспользовать.
3. **Регистратор хранит `k` между раундами** - состояние в памяти; перезапуск
   агентства прерывает незавершённые регистрации.
4. **Хэш `H(R' || m)`** - использовать сжатое представление точки `R'` (33 байта)
   или несжатое (65), но **фиксированно** - иначе проверка разъедется.
5. **Транспорт подлинности** - подписи проверяют содержимое, но не защищают от
   подмены файлов на FTP. Подмена не даст подделать голос, но может устроить DoS.
6. **Версии ключей** - EC-ключи нельзя читать RSA-функциями и наоборот;
   поле `crypto: "ec" | "rsa"` в `config.json` выбирает бэкенд и формат файлов.

## 10. RSA vs EC - сравнение в двух словах

| | RSA (сейчас) | EC (Blind Schnorr) |
|---|---|---|
| Математика | возведение в степень mod `n` | скалярное умножение на кривой |
| Слепая подпись | Чаум, 2 раунда, без состояния | Blind Schnorr, 3 раунда, со состоянием |
| Формат подписи | одно число (мод `n`) | пара `{R, s}` |
| Размер ключа | 2048 бит | 256 бит |
| Стойкость | ~2¹¹² | ~2¹²⁸ |
| Слепота | информационно-теоретическая | информационно-теоретическая |
| Расшифровка до KEYS | 2¹²⁸ (AES) | 2¹²⁸ (AES) + 2¹²⁸ (ECDLP) |

По всем существенным свойствам EC-вариант не уступает RSA-варианту, а по размеру
ключей, стойкости и возможности арифметики на кривых - превосходит. Цена -
дополнительный раунд в регистрации и наличие состояния у регистратора.
